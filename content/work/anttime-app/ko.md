# **1. 상용 DB, 상용 앱 빌드에서 테스트를 하던 불편함을 개선 (프로덕션과 개발 환경 분리)**

- **안드로이드 Flavor와 iOS 스키마 분리**
  - **문제:**
    - 이전 개발자분들은 따로 테스트용 앱을 만들지 않고 신규 기능을 프로덕션용 앱에서 테스트해보고 있었음.
    - iOS 테스트플라이트 / 안드로이드 개발자 계정으로 테스트용 빌드는 생성이 가능하긴 함. 그러나 바라보는 DB가 상용DB여서, 테스트의 부담이 컸음.
  - **조치:**
    - 테스트용 Firestore(파이어베이스의 DB 서비스) 신규 구축
    - 빌드 환경에 따라 상용/테스트DB Firestore Config 별도 주입 파이프라인 구축
      - iOS용 Xcode 빌드 스키마 파이프 분리
      - Android용 Android Flavor를 사용하여 네이티브 빌드 중 react-native-firebase의 환경별 설정 구성
  - **효과:**
    - 개발 생산성 증가. 개발팀이 마음 놓고 변경사항을 배포 테스트해볼 수 있고, 푸시알림 테스트도 손쉽게 할 수 있게 됨.
    - 상용앱과 테스트앱이 모바일 기기 상에서 분리되어, 실제앱을 다운받으려고 테스트플라이트앱을 지우고 할 필요가 사라짐. 빌드할 때마다 오랜 시간 기다리는 비효율 제거.

# **2. 캐릭터의 신체 부위 별로 독립적인 애니메이션 구현 (신체 부위 별 스킨 기초작업)**

1. **React-Native-Reanimated를 사용한 좌표 기반 타임라인 애니메이션**
   - **문제:**
     - 신체 부위 별로 스킨을 교체할 수 있게 하고싶은 비즈니스 니즈 존재. 그러나 기존엔 Lottie라는 애니메이션 툴로, 기본 스킨 애니메이션만 재생됨.
     - 여러가지 스킨 조합의 경우의 수를 표현하는데에 한계가 존재.
   - **조치:**
     - react-native-reanimate로 각 파츠 별 애니메이션 설정. 타임라인 기능으로 각 애니메이션의 실행시기를 정확하게 맞춤.
     - 앱이 백그라운드 상태가 되거나 애니메이션 페이지에서 벗어나면 클린업 함수로 타임라인 제거. 캐릭터 idle 상태로 전환 최적화.
   - **효과:**
     - 신체 부위 별로 따로 동작하는 복잡한 애니메이션을 구현했지만, 앱의 성능을 해치지 않음.
     - 각 파츠별로 새로운 동작, 새로운 스킨을 도입할 수 있는 기틀을 마련

# **3. 신체 부위 별 스킨 아이템 업데이트**

1. **사용자가 앱 내 재화를 소비할 곳이 부족**
   - **배경:**
     - 신체 부위 별 애니메이션 분리 이후, 각 신체 부위 별 캐릭터 스킨을 판매하고자 하는 비즈니스 요구 발생

   - **효과:**

# **4. React Native 버전 노후화로 인한 서드파티 라이브러리 지원 중단 대처 & 마켓 별 최소 요구버전 대응**

[(자세히 보기→)](https://bumang.xyz/ko/blog/24)

1. **Bridge 구조에서 New Architecture로 브레이킹 체인지 유지보수 진행**
   - **문제:**
     - RN 버전 노후화로 인해 서드 파티 라이브러리들의 지원이 중단되는 상황 대처
     - 각 마켓 별 앱 최소 요구버전 상향되는 경우도 존재. 이때 요구사항에 안 맞으면 새로운 출시를 못하게 되는 비즈니스 위험이 존재.
   - **조치:**
     - React Native Upgrade Helper를 사용하여 0.68에서 0.74로 업그레이드하고 그에 맞게 네이티브 코드 수정 (Flipper 제거, Fabric 구성, iOS/Android config 파일 업데이트).
   - **결과:**
     - 앱 성능 개선 (앱 초기 로딩 31% 개선)
       - [측정과정]
         - `adb shell am start -W AnttimeApp/.MainActivity` 으로 TotalTime을 측정.
         - 0.68: 2200ms 대, 0.74: 1500ms 대.
     - 새로운 RN 버전에 맞게 서드파티 라이브러리의 최신 버전도 이용 가능하게 되어 개발생산성 증대
     - 각 마켓 별 앱 최소 요구버전 상향에 대응. 비즈니스 지속을 위해 필수적인 조치 진행.

# **5. 딥링크로 레퍼럴 구조 강화**

1. **PlayStore Referral API 사용**
   - **문제:**
     - 초대를 받아 가입한 유저가 새로 앤트타임을 깐 경우, 추천인의 레퍼럴 코드가 제대로 안 들어있어서 추천 보상이 제대로 지급 안 되는 경우가 발생.
     - 지금까지는 초대 메시지에 있는 Friend’s Referral code를 보고 수기로 입력했어야함. 그런데 많은 유저가 이 부분을 귀찮아하거나 놓침.
   - **조치:**
     - 가장 유명한 딥링크 솔루션인 Firebase Dynamic Links가 지원 중단 예정이어서 차선책으로 Google Play Store Referral API를 사용.
       - Appsflyer등 외부 서비스를 이용하지 말고, 완전 무료 솔루션만 이용하자는 비즈니스 요구도 고려
     - 안드로이드 유저만 사용가능하지만, 전체 유저의 90%가 안드로이드 유저이므로, 커버리지는 높을 것으로 고려.
   - **해결:**
     - 앱 설치 후 진입 시 추천인 링크 쿼리스트링을 자동으로 추출하여 추천인 코드 자동 입력 구현
     - **추천 보상을 못 받았다는 CS 소멸**

# **7. React18 Suspense 패턴**

- **환전 웹페이지에서 로딩/성공/에러 상태 컴포넌트 별 분리**
  - **배경:**
    - 신규 구축하는 환전 웹페이지에서 여러 API를 병렬 호출하고, 로드 되는 순서대로 유효한 데이터를 보여주는 페이지를 만들기로, PM과 디자이너와 논의.
  - **조치:**
    - **Tanstack Query의 useSuspenseQuery와의 조합 활용**
    - Suspense로 Promise를 캐치하여 스켈레톤 및 로딩 컴포넌트를 표출.
    - Error Boundary에 에러 컴포넌트를 물려 상태 별 컴포넌트가 분리되도록 유도.
    - 순차적인 데이터 패칭이 필요한 경우 컴포넌트 마운트 순서를 차등하여 Suspense 패턴 유지
    - 클라이언트 사이드 내에서 API 호출 보장이 필요한 요청의 경우, Suspensive 라이브러리의 ClientOnly 옵션 사용
  - **효과:**
    - 컴포넌트를 상태별로 나눠서 관심사 분리를 시킬 수 있게 됨
    - 컴포넌트 별로 에러/로딩 상태를 관리하기 편하여 병렬 API 호출 후 복잡한 렌더 사이클을 가진 페이지를 효과적으로 개발할 수 있게 됨.
