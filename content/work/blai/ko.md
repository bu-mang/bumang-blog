# **2. 단건결제 시스템에서 구독/결제 시스템으로 전환 — 고객 락인 효과 증대**

- **문제 및 배경:**
  - 기존엔 사용일 충전식 단건 결제 BM이었음. 유저가 사용일수가 떨어지거나, 떨어지기 전에 사용일수를 충전해야 계속 서비스를 이용 가능.
  - 매번 사용일을 체크하고 충전해줘야하는 것이 사용자 경험 상 좋지않다는 지적 존재
  - 유저가 서비스에 락인 되어있지않고 매번 결제 여부를 고민하게 하는 것도 비즈니스 적으로 좋지않다는 판단
  - PG사로 이니시스 사용중이었는데 토스페이먼츠에서 수수료 할인을 해줄테니 옮기라는 제안을 받고, 이왕 PG사 바꾸는 겸 구독전환까지 BM을 진행하자고 결정

- **기획적인 논의 사항들:**
  1. 기존 단건 결제 유저들은 잔여일이 끝날 때까지 구독을 못하게 막을 것인가?
     - 단건 결제자 → 구독 결제 전환 지원.
       기존 사용일이 만료될때까지 추가 결제를 못하게 막는 것은 사용자 경험 상 좋지않음. 구매하러 들어온 유저가 결제를 못 하게 되는 상황은 만들면 안 된다는 판단.
  2. 기존 단건 결제 유저들은 1년치를 충전해놓고 사용하는 유저도 있는데, 이런 유저들이 ‘월구독’을 원하면 어떻게 처리할 것인가?
     - `원하는 티어의 월/연구독 플랜 가치(가격) > 기존에 결제한 티어 플랜의 잔여일 가치` 이면 모두 전환 가능하도록 해주기
     - 전환 불가 상태라도 전환 가능해지는 날짜를 알려주기
  3. 구독 중인데 다른 구독플랜으로 전환하고 싶을 때 업그레이드 해줄 것인가?
     - 이것도 `원하는 티어의 월/연구독 플랜 가치(가격) > 기존에 결제한 티어 플랜의 잔여일 가치` 이면 모두 허용해주기로 결정. 티어를 낮출지언정, 아예 결제 해지를 하지않는 편이 좋다고 판단.
  4. 정기 구독 갱신이 있을 때 기존 쿠폰 시스템은 어떻게 적용시켜줄 것인가?
     - 그리디 알고리즘으로 만료일이 얼마 안 남은 순으로 쿠폰 적용하여 결제가격을 커버할 때까지 적용.
     - 선택된 쿠폰의 가치가 결제액보다 크다면 차액을 새로운 쿠폰으로 발행해줌.
     - 다음 결제일 이전까지 만료되는 쿠폰이 있으면 모두 적용.

- **조치:**
  - 백엔드:
    1. 토스페이먼츠 모듈 추가, 이니시스 빌링 모듈 점진적 제거
    2. 빌링키 발급/콜백/카드변경/자동재결제 cron 구현
       - EKS 상의 pod들이 구독 갱신 cron을 동시에 진행하는 이슈 발생 → 하나의 pod에만 구독 갱신을 돌릴 수 있는 권한을 주어 따로 pod을 띄움. 동시성 경쟁 자체를 제거
    3. 각 구독 티어/기간 별 플랜에서 유저 티어, 단건결제 잔여일 등을 차감하여 최종 결제액이 얼만지 계산하여 프론트로 내려줌 (카탈로그용)
    4. 추후 프론트에서 결제 요청하면 현재 시점에서 티어/기간 별 플랜의 정합성을 다시 체크해서 결제 여부 판단
  - 프론트
    1. 토스페이먼츠 SDK 연동 (빌링 구독 + 단건결제 콜백)
    2. 구독 업그레이드 모달, 플랜 인원수 변경 UI
    3. 현재 잔여일 기준 가치와 비교하여 구독플랜 리스트의 가격이 더 비싼 것만 결제버튼 활성화

- **효과:**
  - 구독결제 전환 및 업그레이드 케이스를 대폭 지원 후, 업그레이드 결제건이 20% 상승.
  - 구독 도입 전월 대비 매출 10% 상승. 그러나 반복매출 상승이라는 점에서 매출의 질이 좋아짐.
  - 기존 단건 결제시에는 ‘만료전 재결제’ 비율이 35~40%였는데 구독 도입 후엔 (일일권 제외) 100% 반복 매출로 전환됨.

# **3. 연속 재결제율 통계, 기능 별 사용량, UTM 유입 통계 등 성장 지표 모니터링 구현**

  - 구독 도입 전, 단건 결제자들이 이용 만료 전에 재결제한 비율이 얼마인지 체크해보고 싶은 니즈 존재
  - 기능 별 사용량이 얼마나 분포되어있는지 통계로 보고싶은 니즈 존재
  - 여러 마케팅 채널들 중 어떤 채널로 많이 유입됐는지 체크해보고 싶은 비즈니스 니즈 존재
- **조치:**
  1. 재결제 비율 계산:
     - 결제 시 마다 해당 유저의 이전 결제가 있는지, 이전 결제 중 가장 최근 결제 건의 만료일이 현재 시점과 비교하여 판별. 진행중인 결제건에 repurchase_type 컬럼 기입.
     - 기존 결제건들도 모두 repurchase_type을 갖도록
  2. 기능 별 사용량 계산:
     - 기능 별 사용로그는 mvp 시점에서도 가지고 있었기 때문에, 이를 따로 통계 테이블로 만들어서 매 일/월/년 계산해둬서 통계 생성하도록 cron job 설정.
  - UTM 유입 통계:
    - 프론트 페이지 초기화 시 쿼리 스트링에 utm으로 시작하는 쿼리가 있으면 세션스토리지에 저장
    - 로그인 안 한 유저가 회원가입 시 세션스토리지에 utm 쿼리 정보가 있으면 유저 정보에 저장
    - 해당 유저가 결제를 발생시킬 때 결제 로그에도 utm 정보 기입
- **효과:**
  - PM 포지션 동료분이 앞으로의 전략 수립을 할 수 있는 기틀을 마련
  - 각 업데이트 마다 직전/직후의 통계를 보며 효과를 수치화. 전사에 공유하며 인사이트를 확충할 수 있도록 개선.

# **4. 슬로우 쿼리 현황 모니터링으로 성능 개선 전략 수립**

- **문제:**
  - 유저 증가로 인해 같은 시기에 간헐적 크롤링 실패 빈도가 증가
    - 단순히 EKS Pod 개수 한도 증가로 해결하기보단 최적화 필요성 대두
  - 제대로 된 슬로우 쿼리 모니터링 시스템이 없음
- **조치:**
  - 크롤러에서 분석 요청 시 걸린 시간 측정.
  - 1000ms 이상 걸린 요청은 db의 슬로우 쿼리 로그 컬렉션(테이블)에 저장
  - 어드민에서 해당 테이블을 조회할 수 있도록 개선. 모니터링 기능 추가
- **효과:**
  - 각 크롤링 분석 기능 별 타임아웃 천장 재조정
    - 기존엔 모든 분석 기능에 일괄 10초 타임아웃 제한이 걸려있었는데, 평균적으로 3초 걸리는 API는 타임아웃 6초로 설정.
    - 어차피 요청이 실패한텐데 긴 타임아웃을 설정해봤자 소용없다는 판단.
    - 전체 처리량 증가.
  - 가장 느린 분석 기능들의 성능 오버헤드를 줄일 방안을 토의할 수 있는 토대를 마련.
